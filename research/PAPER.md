# Polyfish: a Rust forward model for Polytopia research

Manuscript draft for AIIDE 2027. Author and affiliation review pending.

## Abstract

Polytopia-style strategy games combine partial observation, economic development, combat, and several sequential decisions per turn. These properties make them useful for testing planning agents with a forward model. We present Polyfish, a Rust simulator with a browser interface and a seeded headless runner. The initial research scope is two-player Might on 121-, 196-, and 256-tile Drylands maps. A shared interface supports rule-based and rolling-horizon opponents in both interactive games and headless training. We describe the adaptation from earlier Tribes work, test reproducible play under fog of war, and report opening and midgame search comparisons against the Java Tribes reference.

## Introduction and related work

A planning agent needs to enumerate legal actions and evaluate successor states while respecting information boundaries. In a game with several decisions per player turn, the cost of copying or advancing a state can affect how much search fits into a decision. An interactive interface also makes it possible to inspect the concrete actions behind aggregate outcomes.

Java Tribes established a Polytopia-based forward-model benchmark and compared rule-based and search agents. Subsequent work used the environment for pruning and for generating diverse play styles. Polyfish adds an independent Rust environment with the same core research concerns and a local browser interface. Nearby implementations include the C-based Tribes port in `tribes-rl` and the C++ and Python environment PolyEnv. These projects differ in rules lineage, public interfaces, and what has been validated. [Tribes](https://doi.org/10.1609/aiide.v16i1.7438) · [Pruning](https://ceur-ws.org/Vol-2862/paper27.pdf) · [Play styles](https://doi.org/10.1109/cog52621.2021.9619094) · [tribes-rl](https://github.com/pham-tuan-binh/tribes-rl) · [PolyEnv](https://polyenv.readthedocs.io/en/latest/index.html)

## Methods

**Environment.** The release supports two seats, three board sizes, fog of war, and original-capital capture on the profiled Might maps. It records the seed, preset version, and replay commands. We test deterministic turns through save and load and compare the live browser route against the headless runner under the same starting position and human decisions.

**Agents.** The rule-based presets evaluate legal actions according to published Tribes priorities adapted to Polyfish's actions. The rolling-horizon agent evolves a population of one sequence by mutation and evaluates the simulated state at the end of a 20-action horizon. Its input is a belief-state copy built from the acting player's view. The interactive preset uses an explicit budget of 256 advance attempts. The original Java comparison uses the published limit of 2,000 forward-model calls and the original search settings where recoverable. We report these protocols independently.

**Performance.** We benchmark Java Tribes and Rust Polyfish on flat two-capital openings with one warrior per seat and board sizes of 121, 196, 256, 324, 400, and 900 tiles. The operations benchmark times state copy, player-view construction, legal generation, a one-tile movement, and End Turn. A separate trace measures throughput for ten rounds of a fixed script. Both seats alternate one-tile steps and end turns, and each engine enumerates its own legal actions before every advance. We use seven interleaved process pairs per workload and size on one Apple M3 Max with 36 GiB RAM. Each timed process warms up with twice its measured iteration count. The reported intervals resample process pairs. Peak resident set size (RSS) includes runtime memory. One separate memory workload holds 512 copies of the opening state. [Benchmark implementation](run_engine_benchmark.py) · [Reproduction instructions](README.md#reproduce-the-v11-engine-benchmark)

**Profiling.** On the 900-tile trace, the original Rust build spent 2,484 of 6,731 sampled stacks in build-action generation. The profiler showed repeated board scans for neutral roads even before the player had unlocked them, along with allocation of unit, technology, and structure settings. The revised engine shares immutable rule settings, skips unavailable road scans, checks occupied tiles for first contact, and bypasses path search for adjacent steps when the direct move cannot be improved. We also reduced undo bookkeeping for empty work and avoided cloning cities when computing production. Sixty seeded matches produced identical replay commands and results across the two Rust builds. [Profile summary](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/engine-profile-v1.1.json)

**Midgame search.** Both engines load engine-neutral turn-16 positions on all six board sizes. Each seat has two to four developed cities and seven to fifteen units. Preflight verifies that 1,024 prescribed branches per size produce the same normalized seat, round, economy, units, HP, and board changes. The timed full-information workload holds 512 child states across up to five plies, generating the full native legal list for each cloned child before applying the prescribed movement, attack, harvest, or end-turn action. Separate instrumented runs time copying, legal generation, action lookup, and application. Native MCTS starts from each engine's own fog-of-war view and runs 512 iterations with a 20-action rollout cap. Decisions per second include observation construction and reflect each agent's search and evaluation design. [Scenarios and branches](fixtures/midgame) · [Preflight](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/midgame-preflight-v1-tuned.json) · [Reproduction](README.md#reproduce-the-midgame-search-comparison)

**Board layout.** Polyfish stores common visibility membership and tile effects as bitmasks. Standard row-major boards use indexed storage, and sparse or reordered boards use an ordered map. In the mask-only 900-tile profile, reachable-tile computation appeared in 2,479 of 4,143 matched-search stacks and 2,663 of 4,146 native MCTS stacks. We reuse an exploration-checked tile lookup, iterate movement neighbors without materializing a list, and mark occupied squares once per legal enumeration. The occupied-square check retains the existing unit and diplomacy lookup for candidates that can contain a unit. [Staged prototypes and sampling results](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/midgame-profile-v1.json)

## Preliminary evidence and limitations

The pinned Java tournament finished four Capitals games using two published level seeds and both tribe assignments. RHEA and MCTS won two games each. This is a smoke pilot. The upstream runner chooses game and agent seeds from the clock, and its copied forward states can draw from newly initialized randomness. The recorded seeds help identify the runs. [Pilot input](tribes-pilot.json) · [Raw pilot log](results/tribes-pilot.txt)

Before optimization, Rust copied opening states 1.09–1.78× faster across the six board sizes. Java constructed player views, generated legal moves, and applied Step and End Turn faster on the same fixture. Java processed 187,041 scripted actions/s on 256 tiles and Rust processed 42,361 actions/s. Across sizes, the baseline Java throughput advantage ranged from 4.37× to 6.02×. [Baseline data and intervals](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/engine-benchmark-v1.1.json)

After optimization, Rust trace throughput increased 5.1–6.7× across board sizes. In the paired rerun, Rust processed 6.5–11.3% more scripted actions/s than Java. On 900 tiles, Rust rose from 32,592 to 218,319 actions/s, and the paired Java median was 203,916 actions/s. Rust legal generation fell from 27.36 to 3.81 µs per call, near Java's 3.79 µs. Rust Step fell from 10.87 to 2.09 µs and End Turn from 2.47 to 1.33 µs. Java still applied isolated Step and End Turn faster at 1.10 and 0.22 µs, respectively. The engines emitted 13 and 15 legal actions in the opening, respectively, and use different bookkeeping, including Rust's undo callbacks and movement-path visibility. The measurements cover a sparse opening and a scripted trace. [Optimized data and intervals](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/engine-benchmark-v1.1-optimized.json)

In the rerun, median peak RSS on the 256-tile trace was 332.7 MiB for Java and 7.0 MiB for Rust. Holding 512 opening-state copies on the same board size yielded 60.2 MiB for Java and 36.1 MiB for Rust. On 900 tiles the retained-copy workload reached 86.3 MiB for Java and 103.8 MiB for Rust. Process RSS includes runtime and allocator overhead and depends on heap settings. The original pilot's native matches use each environment's own rules and agents and remain a separate workload. [Optimized CSV summary](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/engine-benchmark-v1.1-optimized.csv) · [Original native-match pilot](results/engine-pilot.json)

Across the six midgame boards, the tuned Rust build processed 29.9–34.4% more matched expansions per second and 39.0–45.2% more native MCTS decisions per second than Java. All twelve paired 95% intervals clear a 20% lead. On 900 tiles, Rust reached 8,307 matched expansions/s versus 6,237 in Java, and 1.56 decisions/s versus 1.10. Copying fell from 33.12 to 6.46 µs per expansion in Rust, and legal generation fell from 155.14 to 95.21 µs. Java still applied individual matched moves faster on that board, at 2.58 µs versus 4.05 µs in Rust. Reachable-tile generation remains the largest sampled Rust cost. [Midgame results by board](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/midgame-comparison-v1.json) · [Raw paired runs](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/midgame-benchmark-v1-tuned.json)

Estimated additional Rust RSS per retained state fell by 60.3% on 400 tiles and 58.8% on 900 tiles. On the 900-tile midgame fixture, holding 512 child states required 118.4 MiB before compaction and 52.8 MiB after compaction. The paired Java run reached 201.1 MiB. These workloads include runtime memory and any game state or action lists retained by each engine. We fit the incremental memory estimates to peak process RSS at 0, 128, 512, and 1,024 child states. The tuned build reproduced 9,673 actions from 60 seeded Rust matches and passed the extended simulation undo check. [Baseline runs](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/midgame-benchmark-v1-baseline.json) · [Retained-state results](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/midgame-comparison-v1.json)

Interleaving the two Rust revisions on the original opening trace yielded 39.4–46.0% higher throughput after compaction across the six sizes. In the paired comparison with Java, 512 retained 900-tile opening copies reached 52.0 MiB in Rust and 86.7 MiB in Java. The previous Rust build reached 103.8 MiB on that retained-copy workload. [Rust opening regression check](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/engine-opening-rust-paired-v1.json) · [Opening comparison with Java](https://github.com/HenBOMB/Polyfish/blob/964278e95d9f6cd943f9eaa279b0747e0dad40f8/research/results/engine-benchmark-after-compaction-v1.json)

The browser interface passed setup, tile inspection, turn, board fit, zoom, save, and replay checks. A controlled workflow comparison with the pinned commercial build is still needed before drawing fidelity conclusions.
